## 2. Why change the live core?

The original V0.5 native-adapter experiment used 45 frozen 20,000-operation traces per host (3 sizes 1k/10k/100k, 3 seeds 17/305419896/2654435769, 5 profiles comparison-heavy/update-heavy/short/long/hotspot). Five implementations, 4,050 observations, 3,150 formal timings; independent recalculation covered 450 cells. The tag-range Rust adapter was faster than Full in 45/45 on both hosts, with median Full/tag ratios 1.9712 Windows and 2.2124 Linux; compare-heavy 3.874/5.180; worst about 5.45. List-range wins 43/45 Windows and 44/45 Linux. These are native component comparisons, not isolated abstract algorithm superiority or equivalent full lifecycle guarantees. Example at N100k/seed17 comparison-heavy: Full 3,875,768 requested representation bytes, both OM adapters 13,436,784. See public archive exact original trace/hash and raw data rather than treating this historical timing as contemporaneous with later candidates.

v4.1.0 had intentionally reduced memory against v4.0.0: 1m append 50,249,480 → 42,499,472 requested bytes, 1m/16 retained snapshots peak 513,593,776 → 355,751,040, 10m/2 retained 1,822,185,272 → 1,317,499,808. Historical adverse cases include Linux 3m lookup +10.2% and 4096-byte namespace formatting +25.1% in their original specified comparisons. See [v4.1.0 report at Stable](https://github.com/RXY712200/LayerKeySort/blob/70d7f0ef5857b54381b863d292a213909d87459f/docs/V4_1_0.md) and [integrated memory study](https://github.com/RXY712200/LayerKeySort/tree/6325a6b16d2fe049b7bbc1227c017d6bfb5593b8/benchmarks/research/final-step3). Preserve this advantage while addressing observed speed loss; never infer that all external OM difference originated in 4.1.0. The core formerly computed two absolute AVL block ranks for cross-block comparisons and rewrote all residents' block/local positions for ordinary edits. These costs motivated falsifiable candidates. Related prior art: [Dietz–Sleator](https://www.cs.cmu.edu/~sleator/papers/maintaining-order.html), [Bender et al.](https://erikdemaine.org/papers/DietzSleator_ESA2002/), pinned j-hui/order-maintenance ac4b902d103beb30cee3316d20cd10701f52d15a (MIT; archive preserves actual license/source). Established techniques are not new theoretical discoveries.

Candidate adds one private uint64_t per block; tagged cross-block comparisons direct O(1), same-block local index O(1), any zero tag falls back to original height-guided AVL O(log(1+M)) where M is block count. ## 4. Why B64, not B32, B128 or other block sizes?

This is a historical **two-generation capacity decision**, not an assertion that 64 is mathematically optimal.

1. V4 original decision selected B128 as tunable initial policy (see [V4 decisions, Decision 3 and related sections](V4_DECISIONS.md)). The earlier [V4 Preview.4 report](../V4_PREVIEW4.md), section Sole tuning pass, changed it to B64: B64/B128/B256, eight workload families endpoint/random/local_drag/distant_drag/churn/equal/duplicates/timeline at 10k and 100k, 96 raw rows in each preserved [capacity-screen](../../benchmarks/results/v4-preview4/capacity-screen.csv), [capacity-large](../../benchmarks/results/v4-preview4/capacity-large.csv), [tuned-b64 recheck](../../benchmarks/results/v4-preview4/tuned-b64/capacity-screen.csv). At 100k, B64 lower median totals all eight cells, approximately 7–27% below B128; max local assignments roughly halved, requested live bytes/allocation counts +1–3%. B64 min occupancy 32, bulk restore 65 rows 33/32, physical blocks excluded from wire. Original B128 and post-change evidence retained. These are historical architecture/host measurements, not pooled with 2026-11-24 screens.
2. v4.1.0 deliberately retained B64 while reducing Resident and history memory. The new range updates and block tags materially changed the cost model, so retested B32/B64/B128 rather than assume old result still optimal.
3. In the independent bulk-built 100k state with 4,096 mixed moves, B64 starts 1,563 blocks, ends 1,605; 1,306 same-block and 2,790 cross-block moves, 86 full destinations. Actual logs:

| End state/work | B32 | B64 | B128 |
|---|---:|---:|---:|
| Blocks | 3,190 | 1,605 | 805 |
| Position writes | 108,999 | 168,761 | 281,914 |
| Index-block touch count | 3,950 | 1,637 | 733 |
| Failed tag assignments | 53 | 0 | 0 |
| Zero-tag blocks | 44 | 0 | 0 |
| Requested live bytes (diagnostic) | 3,501,736 | 3,367,376 | 3,299,536 |

Source: [base log](../../benchmarks/research/full-v4.2.0-preview.1.2.1/verification/base-bulk-shapes.log), [B32 log](../../benchmarks/research/full-v4.2.0-preview.1.2.1/verification/b32-bulk-shapes.log), [B128 log](../../benchmarks/research/full-v4.2.0-preview.1.2.1/verification/b128-bulk-shapes.log), [independent flat-sequence model](../../benchmarks/research/full-v4.2.0-preview.1.2.1/bulk_shapes.c). B32 shortens position writes ~35.4%, but index touches ~2.41x and tag pressure increases; B128 reverses tradeoff. This is bulk constructor plus model moves, not itself persisted deserialization; persisted restore verified separately. Counter counts are not measured cache latency or exact causal time. Different capacities produce different physical shapes, as intended; logical sequence/operations controlled.
4. **B8, B12, B16, B96 and other unmeasured capacities:** this cycle does not contain a direct controlled screen of those capacities. Do not claim they were tested, or claim B64 beats every possible size. Current private constraint permits even capacity >=8; smaller blocks plausibly increase metadata per resident, structural updates and tag pressure, but this is a hypothesis and does not establish their actual ranking. B256 has earlier actual evidence, not a current-cycle remeasurement. A defensible paper claim is that B64 was selected against the measured alternatives under two different architecture generations and prespecified resource/performance criteria. If a reviewer later requires a denser capacity sensitivity curve or other workload, reuse these archived tools on a separately identified study; do not rewrite prior decisions or present hypothetical numbers as observations. No automatic reopening of core optimization now.

## 5. Evidence interpretation and future research use

- Separate chronological development experiments, confirmatory tests, negative/rejected options, historical controls and final target production evidence. Do not multiply medians across distinct hosts or pool unmatched campaigns; use contemporaneous within-cell ratios, report all cells and variability. Candidate wins count is not a universal guarantee or proof of statistical significance.
- Preserve raw captures, trace hashes, source/implementation SHAs, exact compiler/flags, binary hashes, receipts, timer protocols and original line endings, failed attempts and decision criteria. Keep licenses and comparator source. No private manuscript/policy/author data in public archives. All original records remain at exact cited commits. This consolidated record is a navigation and decision layer, not a replacement for them.
- Meaningful evidence for future research: two distinct improvements (ancestor + range and bounded tags), two separate candidate rejection processes (midpoint exhaustion, count removal), prospective no-adoption ceiling study, capacity sensitivity over historical and changed representations, independent model/diagnostic verification, real downstream compatibility. Use them as empirical engineering design rationale; do not assert novel theory, general performance dominance, production field traces or fully equivalent lifecycle experiments.
- Unresolved: lifecycle cost, actual downstream cost attribution, larger resource envelope (including million-scale sparse survivors), general tag-health/fallback behavior and selection guidance; cross-language attribution and unmeasured conditions remain limitations. FULL-RI-001/002 scoped design work accepted; no blanket closure of all questions. FULL-RI-006 specific nonzero-tag diagnostic gap closed in c977b0f..., not a confirmed prior production ordering bug.
