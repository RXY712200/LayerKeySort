# Full 选型指南

[English](FULL_SELECTION_GUIDE.md)

Full v4.2.0 是面向动态顺序、稳定排序、批量有序处理及历史顺序的高性能 C17 组件。按任务选择接口：显式 Order 用于相对编辑／先后查询；ManagedOrder 用于稳定比较器插入及查询；`lks_sort` 用于一次性稳定指针数组排序；Group/Batch 用于不可变有序分片和稳定归并；Snapshot 用于独立历史关联、LS1 与恢复。各入口独立，不要求应用同时需要全部能力。

实测的任意相对编辑生命周期优势适用于受测的线索 Treap 与历史副本组合；该组合逐项恢复。采用优化批量构建的 Treap 尚未测量。Full 整合的失败、来源和回调契约有各自的工程意义。

只操作端点时，链式序列加平面不可变历史可以更简单、更快。13 个实测条件中，Full 相对该组合的进程墙钟时间比为 Windows 1.137、Linux 1.136。若需要编辑顺序而无需历史，可依据实际分配和载荷需求比较原生顺序维护（OM）库。所测标签区间 OM 常在小型、更新密集条件中占优。比较包含适配器和工具链的影响。

捕获时复制该快照的关联字节。每次恢复所需的临时指针数量与该快照的行数成正比。数据库场景应单独测量持久化。OrdWeave 的实测显示，全局实例索引发布和刷盘分别主导两种应用模式。替换依赖后，这些职责仍由 OrdWeave 承担。

参见[架构审计](design/V4_2_0_PREVIEW3_ARCHITECTURE.zh-CN.md)和[阶段证据](V4_2_0_PREVIEW3.zh-CN.md)。

## 选型边界与既有机制

| 条件 | 证据及预算 |
| --- | --- |
| 任意相对编辑与已索引历史 | 对齐 1k/10k/100k 的研究中，最终版相对线索 Treap 的进程墙钟比为 Windows 0.580、Linux 0.526。受测 Treap 逐项插入恢复。平衡的批量恢复未测。 |
| 端点编辑与平面历史 | 13 个条件的 Full / 平面组合比为 Windows 1.137、Linux 1.136；可优先评估平面组合。任意先后查询的成本会不同。 |
| 无历史的先后查询与编辑 | Full / 原生标签区间为 1.052/1.020，Full / 原生链表区间为 0.909/0.926。小型更新密集条件有利于原生 OM。工具链、分配器与适配器有差异。 |
| 比较器驱动编辑 | ManagedOrder 保留等值实例的稳定先后并提供边界查询。比较器与上下文均借用，必须保持顺序不变量。显式顺序的测量无法替代等价的托管顺序比较。 |
| 持久应用 | OrdWeave 重放支持适配器兼容性。最终版相对 Preview.1.2 的应用操作延迟比分别为内存 1.002、持久化 0.997。WAL 和全局发布应单独预算。 |

[协议](../benchmarks/research/full-v4.2.0-preview.3/PROTOCOL.zh-CN.md)改变快照频率、历史保留量、关联字节数和命名空间，并设置独立留出历史。实时顺序回放每个条件运行七次正式测量。OrdWeave 每个条件运行三次正式测量和一次预热，另行采集归因数据。测量结论适用于列出的负载类型；未推导统一的交叉点。保留快照需要复制字节和行尾偏移。恢复除新 Order 外还需 N 个临时指针。分别测量请求保留量、请求峰值、驻留内存、线格式大小和分配流量。Treap 的大范围捕获诊断不含实时序列字节，留出组单独计入这些字节。

Dietz 和 Sleator 的顺序维护研究处理动态插入、删除和先后查询。Bender、Cole、Demaine、Farach-Colton 和 Zito 提出了更简单的标签方法。Full 结合已有的标签、有界块和 AVL 回退、独立分配的 Handle 以及不可变历史。工程价值在于跨操作保持统一的实例、来源与失败语义。测量考察整合后的设计与成本。见[原生 OM 实现](https://github.com/j-hui/order-maintenance/tree/ac4b902d103beb30cee3316d20cd10701f52d15a)。

应用需要这些保证时，替代组合必须自行实现稳定身份、版本与来源、捕获复制、线格式校验、有序解析和发布规则。对照组对齐成功操作；可恢复失败和回调的契约有区别。持久标识、数据库结构、WAL、解析回调副作用与外部同步由应用负责。需要独立测量数据库原生索引、Treap 批量恢复和持续保留多百万实例的历史。
