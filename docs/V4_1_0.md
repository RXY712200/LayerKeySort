# LayerKeySort Full v4.1.0 — compatible optimization record

The three independently reviewed Full optimization steps are **merged into
`main`** through protected [PR #19](https://github.com/RXY712200/LayerKeySort/pull/19),
exact main commit `7fef6396cba4f5f8d19516b9ae2af132ca3cd529`.
This makes the main-branch **source version 4.1.0**. The most recently published
Full Stable is still v4.0.0 until new annotated tag and release assets exist.

## What changed

- Live order: share owner metadata at the Block level while retaining stable
  separately allocated Resident addresses, B64 occupancy and implicit AVL indexing.
- Historical snapshots: use cumulative per-row association ends; coallocate
  header/row/Namespace storage; retain only the exact useful association capacity
  after successful capture.
- Build/distribution validation: always configure Debug for the established Debug
  build/install test flow on implicit Windows single-config generators.
- Maintain source compatibility with the frozen 64-function/14-type v4 API.
  LS1 and LKS4SNP1 wire bytes, V3 LK1 migration, callbacks, borrowed items,
  handle lifetimes and existing OOM guarantees remain unchanged.

## Measured memory improvement (x64, Full requested bytes)

| Workload | Original 4.0.0 | Combined candidate | Reduction |
| --- | ---: | ---: | ---: |
| 1m source Append | 50,249,480 | 42,499,472 | 15.4% |
| 1m/16 retained snapshots, whole requested peak | 513,593,776 | 355,751,040 | 30.7% |
| 10m/2 retained snapshots, whole requested peak | 1,822,185,272 | 1,317,499,808 | 27.7% |

These are requested allocator bytes, **not** whole-process peak resident memory.
At large sizes, callback, payload and allocator-specific effects still matter.

## Performance limitations

This is not a universal speedup. In a measured Linux 3m random lookup trace,
the combined candidate was 10.2% slower than the original baseline. A specialized
large-Namespace key-format trace was 25.1% slower than the Step 1 candidate.
Some wide serialization, churn and destruction phases also regressed. Final
association trimming can increase requested allocation traffic for wide data.
Consumers with strict budgets for these particular workloads should benchmark
against the 4.0.0 Stable release.

Resident allocation count, B64 slack, full independent snapshot ownership and
the 8N resolve-first restore-pointer scratch remain accepted costs.
