# 负载模拟器方法

历史原文：[benchmarks/WORKLOADS.md](https://github.com/RXY712200/LayerKeySort/blob/fd7e3e7d15b5b8fc35ff0bfb0ffbafe5c94b5111/benchmarks/WORKLOADS.md)（英文）。本译文记录当时的 v3.1.0 测量。

本研究为已发布 v3.1.0 补充**合成应用类负载**证据。它不来自真实用户轨迹，也未修改生产算法。源码为 `workload_simulator.c`，`run_workloads.py` 使用 Python 标准库。CMake 仅在 `LKS_BUILD_BENCHMARKS=ON` 时构建。

## 负载模型（在采集前冻结）

每个驻留项有一个有符号 64 位合成键、唯一对象 ID 及新的插入序号。公开比较器只比较键。等键保持序号顺序。按键查询删除时选择该键的第一个、最早插入的驻留项。因此，随机选择活跃键的权重按键桶分布，与在等值对象间均匀选取不同。更新先删除对象，在其不驻留时修改键，再插到新等值区间末端。驻留期间不修改参与比较的字段。

| 类型 | 操作模型 | 键模型 | 数量 |
| --- | --- | --- | --- |
| `timeline` | 70% 近末端新建、15% 尾部回填、5% 广域新建、10% 删除 | 初始 `i*1024`；近末端使用历史最高水位加 1..1024 均匀整数，回填减 1..65536，广域在 0..最高水位 | 每操作约增 0.8 项 |
| `priority` | 35% 新建、25% 删除、40% 删除/修改/重新插入 | 初始、新建及修改后的键均为 0..31 | 每操作约增 0.1 项 |
| `local` | 10% 新建、10% 删除、80% 删除/修改/重新插入 | 初始 `i*1048576`；新键为随机驻留项的键加减 1..8 个初始间距；90% 更新将已删键移动正负 1..8 个间距，10% 跳到另一驻留项附近正负 128..1024 个间距 | 大体稳定 |
| `churn` | 30% 新建、30% 删除、40% 删除/修改/重新插入 | 初始 `i*1048576`；普通新键范围 0..initial*1048576；5% 新建、10% 更新提议超出历史极值一个间距 | 保持目标的 +/-5% 区间 |

这些比例是建模假设。timeline 模拟事件迟到，priority 覆盖变更中的稳定等值桶，local 模拟数值距离重排，churn 覆盖长时间修改。数值距离不等于确切秩移动，模型也不代表所有编辑器。churn 在上下界改派新建或删除提议；任一类型在驻留项少于两项时强制插入。记录实际操作次数。

每项操作消耗一条确定的 xorshift32 轨迹。即使未使用的提议也推进随机状态，精确复现需使用同一实现与场景参数。取模产生小幅偏差，分辨率为 32 位。键算术和 CLI 规模均检查，种子须非零。

七种对照复用 `current_benchmark.c` 的定义，保持该文件不变：升序 `i`，降序 `N-i`，随机为 `i` 的 Fisher–Yates 排列，全等为 `0`，重复为 `xorshift32%32`，交替为偶数 `i/2`、奇数 `N-1-i/2`，热点先 `0` 后 `N-i`。其中 `N=initial+operations`，initial 是不计时前缀。这些对照只插入；即使初始规模与观测长度相同，也与混合场景的操作组合不同。

## 计时与正确性

初建为不计时预热，之后的测量操作均保留。逐插入计时器只包围 `lks_ordered_tree_insert()`。查找、删除、生成键、参考排序、采样分析和调度均在外。更新延迟仅表示重新插入；独立保留包括全部开销的进程墙钟时间。

C17 `timespec_get(TIME_UTC)` 的纪元毫秒方法与既有基准相同。它是墙钟而非单调时钟，负间隔使运行中止。该纪元附近 double 的粒度约为 0.000244 ms，实际时钟与调度影响可能更大。零值和亚微秒百分位不支持可靠差异判断。分位使用最近秩法。至少 10,000 次插入（至少十个上尾样本）才输出 P99.9。最大值是实测值，不能作为时延上界。

生产和诊断程序顺序执行相同轨迹，生产先行。轨迹和检查点坐标摘要必须一致。诊断时延含分配与计数插桩，不用于代表生产性能。操作下标可对齐事件，但两个时间来自独立运行。

在第零项、固定间隔与结尾，平面参考数组按键和插入序号排序，独立于 Path 编码与 AVL 形态。检查总数、各身份、创建对象的成员完整性、稳定等值、严格 Path 次序，以及 32 项首等值定位和确切 Path 查找。此验证按检查点进行。CI 参考模型自检蓄意损坏等值次序及成员关系，并确认拒绝。失败打印完整参数及检查点；定位区间内首次出错可能需要更密的检查点。

## 工作量增量、抽样与内存

对每次诊断插入，计算私有修复累计计数前后差。`nodes_relabelled` 为被替换坐标的既有节点数。全区间单独标记；直方图互斥区间为直接插入、1..8、9..32、33..128、129..512、513..4096、4097+、全区间。局部指不超过 128 个旧节点，大范围指超过 128，另外区分全区间。尝试节点是各尝试窗口求和，与最大尝试窗口不同。不对累计最大值取差来构造单事件计数。插入深度为实际提交的新 Path 深度，排除被拒绝的候选坐标。

普通输出保存最慢 25 次、重标规模最大 25 次及最先 5 次全区间事件的并集（每运行诊断不超过 55 行、生产不超过 25 行）。`sample_flags` 的三个掩码值 1、2、4标识这些来源。C 的 `--trace` 可输出全部插入供调查，普通证据不包含它。

检查点剖析遍历所有驻留项的 Path，记录深度平均/P95/P99/最大值、显示文本及 LK1 平均/最大长度、驻留项的 Path 字节与总 LK1 载荷字节。长度不含 NUL，C 字符串每项另需一字节。驻留项的 Path 含对象与已分配步骤容量。诊断只计算库分配，不含模拟数组、Python、分配器头或 RSS。请求字节为累计流量；存活和峰值为同时存在的请求内存。累计总量含准备，测量历史增量不含准备。销毁后库中仍在使用的请求字节须归零。高分配流量与泄漏是不同指标。

## 复现

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DLKS_BUILD_BENCHMARKS=ON
cmake --build build --parallel
python benchmarks/run_workloads.py --timed build/layerkeysort_workload \
  --diagnostic build/layerkeysort_workload_diagnostics --smoke
python benchmarks/run_workloads.py --timed build/layerkeysort_workload \
  --diagnostic build/layerkeysort_workload_diagnostics --campaign \
  --output /path/to/new-results --compiler gcc --machine "describe machine"
```

Windows 使用 `.exe`；MSVC 多配置可执行文件位于 `build/Release/`。诊断目标需要 `LKS_BUILD_TESTS=ON`（顶层默认）。驱动拒绝覆盖已有采集文件，要求模拟器已提交。完整方案见 `campaign_plan()`：两个小种子、五个主中型种子、一个大种子、选定长 churn、七种对照的小中规模，末尾为保留的中型及长时留出。CI 仅用初始 128 项和 512 次操作，另检查畸形 CLI 与输出。

结果与边界见[原始证据报告](../docs/WORKLOAD_EVIDENCE.zh-CN.md)。冒烟场景用于验证流程。
